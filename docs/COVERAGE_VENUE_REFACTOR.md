# Coverage identity refactor — Ikaros `feature/clean_s`

This change separates three independent concepts:

| Concept | Meaning | Example |
| --- | --- | --- |
| `VENUE` | Market/exchange association | `GPW`, `CBOE` |
| `INSTRUMENT_TYPE` | Financial instrument class | `EQUITY`, `INDEX`, `FUTURE`, `OPTION` |
| `DATASET` | Internal source/ingestion workflow; **not** instrument identity | `GPW`, `WIG20`, `DERIVATIVES` |

`DATASET` **remains unchanged** in backfill jobs, staging, promotion, CLI flags, and IIC. Renaming it throughout the app would break legitimate routing semantics. Only the *coverage report* stops using it as a classification.

## Report layout

The WIG20-history `coverage.csv` now has:

```text
venue,instrument_type,symbol,accepted_sessions,missing_sessions,first,last,status,listing,source_observations,rejections,source_errors
```

Examples (illustrative values, not actual price coverage):

```csv
venue,instrument_type,symbol
GPW,INDEX,WIG20
GPW,EQUITY,PZU.WA
GPW,FUTURE,FW20Z2620
GPW,OPTION,OW20L264250
```

- Equity `VENUE` and `INSTRUMENT_TYPE` are resolved from `SECURITIES` (`stock`/`equity` is normalized to `EQUITY`). The report rejects missing, ambiguous, or non-equity references.
- Derivative identity comes from `DERIVATIVE_CONTRACTS.VENUE` and `DERIVATIVE_CONTRACTS.INSTRUMENT_TYPE`; source code does **not** infer venue from `FW20`/`OW20` prefixes, type, or underlying.
- WIG20's `GPW` value is the explicitly reviewed **market association** of the benchmark, *not an execution venue*. WIG20 index levels are not exchange-traded contracts. For other indices, a proper index master / associated-market reference must be introduced; unsupported indices are rejected rather than guessed.
- `OPTION` means an instrument type; `CALL`/`PUT` remains `OPTION_SIDE`, not a venue or an instrument type.
- `missing_sessions` remains blank for derivatives: an illiquid option need not trade on every GPW session. It remains a numeric count for index and constituent equities.

## One additive local database migration

`DERIVATIVE_CONTRACTS` gets a nullable `VENUE VARCHAR`. `SECURITIES.VENUE` already exists. `LocalDuckDBRepository.prepare_tables()` runs the existing additive reference-schema migration on repository open; no manual SQL migration or new setup step for newcomers.

**Existing contract rows are not assigned a venue based on their underlying, symbol prefix, or the absence of other exchanges.** Until a reviewed source confirms the venue, the field remains `NULL`. New registrations in the standard local bootstrap may read either legacy four-column CSVs (unknown venue) or a five-column manifest with explicit `venue`. A conflicting existing, non-null `VENUE` is rejected.

The bundled WIG20 reference contracts and the WIG20 listing adapter explicitly declare `venue=GPW`. Contracts with an explicitly different venue are excluded from this GPW-specific history run and listed under `excluded_non_gpw_contracts` in `summary.json`; unresolved venues are retained but flagged. These are registered through the existing `store_contracts` reconciliation logic; NULL venues are populated, but conflicts are never overwritten. The full-history report writes a blank `venue` for unresolved records, lists contract IDs in `summary.json` as `contracts_missing_venue`, and returns incomplete status.

No existing price rows are changed; no price history is generated or overwritten. In particular, `PRICES`, `INDEX_PRICES`, `DERIVATIVE_PRICES`, all candidate tables, and provider mappings need **no data migration for this local reporting refactor**.

## Reclassify an existing coverage.csv without downloading prices

First activate the existing named `Ikaros` environment (as documented in the main README), then from the repository root:

```powershell
python -m run.prepare_daedalus --reference-only
# Optional but recommended: refresh reviewed current GPW derivative listings without requesting prices.
python -m run.backfill_wig20_universe --inventory-only --write
# Preview only (no CSV output; repository initialization can apply additive DDL)
python -m run.reclassify_coverage
# Write output/wig20_history/coverage_venue.csv, preserving coverage.csv
python -m run.reclassify_coverage --write
```

The original coverage CSV is **never overwritten** by the reclassifier. It refuses to overwrite an existing `coverage_venue.csv` so that prior reports are not lost. The normal next full backfill run writes `coverage.csv` directly in the new format, so the reclassifier is needed only for reports generated by older code.

If a contract was registered outside the reviewed GPW listings, its `VENUE` may remain NULL. The report writes a blank venue and flags it. Add a reviewed venue to `data/derivative_contracts.csv` (or use an appropriately reviewed reference importer) and rerun registration. The code **never** silently substitutes `GPW` for missing evidence.

No script is placed in the repository root, no dependencies are added, and newcomers who use `setup-ikaros.cmd` receive the new schema automatically.

## DB consequences for other exchanges (separate future migration)

| Table/domain | Current state | Future multi-venue requirement |
| --- | --- | --- |
| `SECURITIES` | Has `ASSET_ID`, `VENUE`, `INSTRUMENT_CLASS` | Existing fields suffice for this report; validate asset identity per venue |
| `DERIVATIVE_CONTRACTS` | **Add `VENUE` now**; `CONTRACT_ID` remains global primary key | Prefer stable `CONTRACT_ASSET_ID` or composite `(VENUE, CONTRACT_ID)` identity |
| `DERIVATIVE_PROVIDER_SYMBOLS` | References `CONTRACT_ID` | Re-key provider mappings to venue-qualified contract identity |
| `DERIVATIVE_PRICE_CANDIDATES` | References `CONTRACT_ID` | Re-key staged candidates similarly |
| `DERIVATIVE_PRICES` | References `CONTRACT_ID` | Re-key accepted prices similarly; preserve old foreign keys and provenance |
| `INDEX_PRICES` / index master | `INDEX_SYMBOL` is used as key | Add explicit index master with associated market and administrator when adding other indices |
| Snowflake `DERIVATIVE_CONTRACTS` | Managed separately from local DuckDB | Requires own additive `VENUE` migration **and** updates to its registration writers before accepting foreign exchange derivatives |

**Important:** a venue column alone does not solve collisions where two exchanges list the same `CONTRACT_ID`. This package does *not* claim to implement multi-venue derivative storage. It improves metadata and reporting for the current GPW WIG20 universe while surfacing gaps instead of concealing them.
